# نتائج الفحص وحدود الاعتماد

28 أكتوبر 2026، تنفيذ محلي على الفرع `codex/secure-turso-rebuild`. البيانات في الاختبارات مصطنعة؛ لا أسرار أو بيانات موظفين أو اتصالات بالقواعد الحالية.

## نتائج ناجحة

- اختبارات المجال/الأمان/SQL والاستيراد والـpolling: 17 اختبارًا في التشغيل الشامل، ثم أضيف اختبار رفض التاريخ غير الموجود ونجحت مجموعة الاختبارات المتأثرة (6 اختبارات)؛ مجموع السيناريوهات الحالية 18. لا failures أو skipped في هذه التشغيلات.
- `npm run build`: تجميع Wrangler dry-run ناجح، دون deployment.
- `npm run test:runtime`: login → commit → list/changes → retry على **Cloudflare workerd + Durable Object SQLite + official libSQL HTTP client** أمام SQLite فعلية محلية. شمل scrypt في محرك Workers ومطابقة cookies وCSRF والصلاحيات وغياب طلبات DB أثناء version polling القصير.
- `npm run test:dom`: شغّل كود الواجهة الحقيقي في jsdom مع الخادم نفسه. تسجيلان = مهمتان و17 عنصرًا، وضياع رد commit ثم retry يحافظ على صف واحد، وظهور النتيجة المؤكدة في الواجهة، واستكمال شاشة مستخدم آخر بالمؤشر، وإخفاء مصادر الأرشيف عن operator. هذا اختبار وظائف DOM وليس فحص layout بصريًا.
- اختبرنا 30 إعادة محاولة متزامنة من عميلَي SQLite مستقلين: صف واحد وحدث واحد. ثم 30 تسجيلًا مختلفًا متزامنًا بملخصات صحيحة.
- failure injection داخل تحديث ملخص اليوم ألغى المهمة وسجل التغيير والإجمالي داخل المعاملة نفسها. فشل تخزين مؤشر DO **بعد** commit ثم restart لم يفقد المهمة، وretry أكد نفس ID ولم يزد الإجمالي.
- import بــ26 عمودًا و20 عمودًا: عناوين فارغة ومتكررة، Unicode، أصفار بادئة، commas/quotes/newlines، استئناف دفعات بعد الفشل، رفض تغيير بصمة المصدر، ومنع إدخال الملف نفسه تحت مصدر آخر. لم نختبر الملفين الحقيقيين لأنهما غير موجودين هنا.
- backup/restore مستقل محلي مع integrity_check وبصمة كل صف وقيمه، دون تعديل المصدر. بيانات مصطنعة فقط.
- `node scripts/test_all_pages.js` من جذر المشروع: نجحت اختبارات rendering القديمة المعتمدة على mocks. اختبارات قديمة تحتاج secrets أو backups غير موجودة لم تشغّل على بيئة فعلية.
- `npm audit --omit=dev --audit-level=high`: لم يرصد vulnerabilities في dependencies الإنتاجية في وقت الفحص. لا يمثل مراجعة أمنية مستقلة كاملة.

## فحص المتصفح البصري

أضيف اختبار Playwright يصور desktop وmobile، ويختبر retry بعد ضياع رد الحفظ وإعادة فتح الصفحة، ومستخدمًا ثانيًا مع polling، وoverflow على عرض 390px. **لم ينجح تشغيل Chromium في الحاوية الحالية**: تنزيل المتصفح أرجع ملفًا غير صالح، والبديل المحلي خرج بإشارة SIGTRAP. لذلك لا توجد screenshots معتمدة ولا قياس متصفح حقيقي لزمن الـ15 ثانية في النتائج المحلية.

CI يحتوي تثبيت Chromium وتشغيل الاختبار من أجل إكمال هذا الفحص في بيئة تدعمه. اقرأ حالة CI الفعلية، ولا تعتبر وجود الاختبار نجاحًا له. مراجعة الشكل على هاتف/متصفح حقيقي جزء متبقٍّ قبل الإنتاج.

## سيناريو استهلاك واقعي محلي

[القياسات وخطط التنفيذ](benchmark.local.json) ناتجة من تنفيذ كود API/المعاملات الفعلي على SQLite محلية، بساعة افتراضية، وليست اختبار حمل سحابيًا أو تشغيلًا فعليًا لمدة 8 ساعات.

| الافتراض | القيمة |
|---|---:|
| شاشات مفتوحة طوال الوردية | 30 |
| operator / supervisor | 27 / 3 |
| مدة الوردية الافتراضية | 8 ساعات |
| فاصل version polling | 15 ثانية |
| تاريخ live موجود قبل البداية | 50,000 صف مصطنع |
| معدل التسجيل لكل operator | 6/ساعة |
| إعادة المحاولة | كل تسجيل رقم 20 |
| افتراض الشهر | 22 يوم عمل |

| ما قيس فعليًا محليًا | النتيجة |
|---|---:|
| تسجيلات جديدة | 1,296 |
| retries مؤكدة لنفس المفتاح | 64 |
| طلبات مؤشر الإصدار | 57,600 |
| طلبات changes عند تغير النطاق فقط | 5,184 |
| استدعاءات عميل DB أثناء الحمل، بما فيها فحص الجلسات | 20,914 |
| SQL statements للتطبيق، دون transaction-control statements | 28,818 |
| تعديلات صفوف SQLite بما فيها triggers، دون احتساب index maintenance | 7,776 |
| إجمالي API مع login وصفحة البداية في هذه المحاكاة | 64,204/يوم |
| امتداد العدد إلى 22 يوم عمل | 1,412,488 طلب API |

إعادة فحص الحسابات كل 60 ثانية سبب جانبًا من استدعاءات DB. جدول SQLite في DO يجيب عن version خلال هذه الفترة دون كشف تغييرات عبر قراءة Turso. تخفي الواجهة polling أثناء غياب الصفحة، لكن المحاكاة افترضت عدم إخفاء أي شاشة لإظهار حمل أكثر تحفظًا. طلب `/api/me` الأول والأصول الثابتة وحركة التطبيقات الأخرى تضيف طلبات خارج workload الجدول، وكذلك الأخطاء/إعادة الاتصالات قد تزيد الاستهلاك.

راجعنا EXPLAIN QUERY PLAN للاستعلامات المنفذة: lookup المفتاح باستخدام unique index؛ changes الخاصة بالمستخدم عبر `(owner_id,seq)`؛ changes الفريق عبر INTEGER PRIMARY KEY range؛ ثم task lookup بالـprimary key، وملخص scope بصف محدد. لا task-table scan أو temporary ORDER BY في هذه الخطط. هذا دليل على المسار المخطط؛ **ليس عداد rows_read من Turso**، ولا يعني أن صف نتيجة واحد يساوي قراءة مدفوعة واحدة.

`actual_turso_rows_read` و`actual_turso_rows_written` في التقرير = **null**. لا اتصال سحابي متاح لإثباتهما. script `measure-turso.mjs` جاهز لاختبار منفصل باسم `meti-bench-*` وبقراءات Usage API الرسمية، مع أخذ تأخر العداد في الاعتبار. لا تعتمد capacity نهائية قبل إتمامه، ولا تستخدم عدد النتائج أو total_changes بدل عدادات الخدمة.

## الحدود الحالية والمخاطر المحددة

تمت مراجعة المصادر الرسمية بتاريخ 28 أكتوبر 2026:

| المنصة/المقياس | الخطة المجانية الحالية |
|---|---:|
| Turso monthly rows read | 500 مليون |
| Turso monthly rows written | 10 ملايين |
| Turso total storage | 5GB |
| Workers requests | 100 ألف/يوم |
| Workers CPU/request | 10ms |
| Durable Objects requests | 100 ألف/يوم |
| Durable Objects duration | 13,000 GB-s/يوم |
| DO SQLite rows read/written | 5 ملايين / 100 ألف يوميًا |
| DO SQLite total storage | 5GB |

حصة Turso تشمل القواعد الثلاث وسائر الحمل في Organization. توزيع الأرشيف لا ينشئ ثلاث حصص. تجاوز Free limits قد يوقف العمليات؛ paid overages وpricing تغير سياسة التكلفة ولا يضمنان budget ثابتًا. لا نفترض تفعيلهما.

30 مستخدمًا في السيناريو يقعون نظريًا دون حد **عدد طلبات** Workers/DO وحده، مع هامش للطلبات الإضافية. لم نقس CPU أو duration أو DO billed rows على Cloudflare فعليًا، لذلك هذا ليس إثباتًا لملاءمة Free. المنسق الواحد يسلسل المعاملات، لذا RTT إلى Turso وحمل login/import/report يمكن أن يزيدا الانتظار؛ queue مقيدة بـ100 طلب، وطلبات DB بمهلة 10 ثوانٍ، ويجب قياس P95 وزمن المعاملات في المنطقة المقصودة.

100 مستخدم × 8 ساعات × 3,600 / 15 = **192 ألف version request/يوم قبل POST/changes/login**. هذا يتجاوز الحد المجاني اليومي لــWorkers وDO. عند هذا الحجم يلزم قرار بين فاصل أطول بزمن ظهور معلن، أو WebSocket Hibernation مقاس فعليًا مع نفس سجل الاستكمال والصلاحيات، أو خطة مناسبة. لم يُنفذ broadcast عبر isolate Map.

مراقب Organization Usage يصدر workflow failure عند 70% بعد ضبط الأسرار واعتماد الـworkflow على الفرع الافتراضي؛ ليس نشطًا في الحساب بمجرد إنشاء PR. فعّل إشعارات Actions وCloudflare metrics لدى مالك التشغيل. واردات الأرشيف والتحقق والـbackup والـindexes تستهلك أيضًا حصة مشتركة لمرة النقل، ولا تدخل أرقام حمل التشغيل أعلاه.

## نقاط الاعتماد المتبقية

1. مراجعة UI في متصفح فعلي ومراجعة حالة CI.
2. توفير الملفين الأصليين في المحادثة، والتحقق من 54,539×26 و34,635×20 وعناوين الصفحات والعينات. لا توجد موافقة ضمنية على تعديل القواعد القديمة.
3. اعتماد قاعدة تعدد التسجيلات ومعاني الأعمدة وparser التاريخ وحدود عدم التداخل. مجموع all يبقى غير متاح قبلها.
4. تهيئة بيئة مراجعة خاصة وأسرارها خارج الدردشة، وقياس Turso/Cloudflare الفعلي وbackup/restore للمصادر الحقيقية.
5. اعتماد منفصل قبل تحويل الإنتاج وتعطيل مصادر التسجيل القديمة. لا merge أو deploy أو استيراد حقيقي ضمن التحقق المحلي.
